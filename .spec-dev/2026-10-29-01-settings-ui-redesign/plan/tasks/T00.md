### 任务 0：建立隔离工作区

**交付与验证**：在本计划专属 worktree 中得到可构建、`--self-test` 通过的基线，记录来源与基线 SHA。无 spec Scenario；为后续全部任务提供隔离（spec「风险」改动面广）。

**文件**：
- 修改：`.gitignore`（仅当 `.worktrees/` 尚未被忽略时追加 `/.worktrees/`）

**接口**：
- 产出：实施 worktree `<来源根>/.worktrees/plan/2026-10-29-01-settings-ui-redesign`，分支 `plan/2026-10-29-01-settings-ui-redesign`；progress `notes` 中的来源根 / 来源分支 / 来源 HEAD / 实施路径 / created 归属。

**执行前提**：执行前先按 index「与 fix/code-audit 的衔接」确认 main 是否已合入 fix/code-audit，并决定实施分支基点（默认：本计划所在分支 `feat/ui-redesign-spec` 的当前 HEAD，它包含 spec 与本计划）。

**步骤 1：检测已有隔离**

运行：`git rev-parse --git-dir` 与 `git rev-parse --git-common-dir`
两者不同、且 `git rev-parse --show-superproject-working-tree` 无输出（排除 submodule）
→ 已在隔离工作区，只跳过步骤 2 的创建，仍执行下面的绑定、步骤 3 与完成状态保存。

在创建前记录实际来源工作区绝对路径（`git rev-parse --show-toplevel`）、来源分支（`git branch --show-current`，预期 `feat/ui-redesign-spec`）与 HEAD（`git rev-parse HEAD`）；创建后记录实际实施工作区与分支。复用时从原隔离机制的记录核对来源，不能由 common-dir 推算来源工作区、假定来源为 main 或把复用资源改为本计划所有。用现有 append-only `notes` 保存这些真实值、created/inherited 归属及移交方式；`resources` 中复用行写保留/移交回执，不能预填删除命令。无法核实的来源明确记未知，不能据此生成合并命令。

**步骤 2：建立 worktree**

先按 using-git-worktrees Step 1 核对执行能力，并将新建目标固定为 `<实际项目根>/.worktrees/plan/2026-10-29-01-settings-ui-redesign` 的绝对路径；路径不得逃逸，已有 `worktrees/` 或宿主默认目录不改变目标。
两种机制创建前都确认 `.worktrees/` 已被忽略（在项目根运行 `git check-ignore -q .worktrees/`，未忽略先将 `/.worktrees/` 加入根 `.gitignore` 并提交：`git add -- .gitignore && git commit -m "chore(T00): 忽略 .worktrees/"`）。只有能明确指定或确认使用目标路径的宿主原生入口才优先；仅名称参数、路径能力未知或目标不同则直接使用 Git。原生失败时先核对遗留资源，允许安全降级才继续：
`git -C "<实际项目根>" worktree add "<实际项目根>/.worktrees/plan/2026-10-29-01-settings-ui-redesign" -b "plan/2026-10-29-01-settings-ui-redesign"`。
创建后核对回执与 `git worktree list --porcelain` 中的实际路径再进入；路径不符时停止后续写入并报告，不自动搬移、删除或重复创建。Step 1 已复用的工作区保留原位置，不因新目录规则自动迁移。

在现有 notes/resources 中记录宿主原生或 Git 管理、实际根/分支及恢复入口。progress.yaml 已预登记 `worktree: .worktrees/plan/2026-10-29-01-settings-ui-redesign —— git worktree remove .worktrees/plan/2026-10-29-01-settings-ui-redesign`；若步骤 1 判定为复用，把该行改为保留/移交回执。一次 Bash 的 cd 不证明会话或其他文件工具已切换；首次绑定前核对实际工具 cwd。Git 降级后的普通会话不因恢复而无条件 EnterWorktree 接管，已有原生隔离会话也不自动移出。

**步骤 3：安装依赖并验证基线**

项目无包管理器与锁文件；构建只需 Xcode 命令行工具（`xcrun swiftc --version` 有输出）。缺工具时报告缺口，不自行安装。
按 index「相关测试范围」运行基线验证（在实施 worktree 根目录）：

```bash
./build.sh && .build/miremote --self-test; echo "exit=$?"
```

预期：末行 `SELF-TEST PASS`，`exit=0`。同时在 notes 记录 `xcrun swiftc --version` 的输出（判断是否为 Swift 6.2 / Xcode 26，决定液态玻璃分支是否会被编入，见 index D4）。
声明命令执行报错或工具不可用 → 停下报告，不回退完整测试套件（完整套件在 T19 首次执行）。基线测试失败 → 停下报告，先问再继续。

将已验证的实际基线 SHA 写入 T00.commit，保存 T00 completed 检查点；步骤 2 跳过不意味着 T00 无需落盘。状态写入采用同目录临时文件 + rename，保留原 tasks/notes/resources；状态提交独立于它引用的实际基线提交：`git add -- .spec-dev/2026-10-29-01-settings-ui-redesign/plan/progress.yaml && git commit -m "chore(T00): 记录隔离与基线"`。

**降级**：非 Git 仓库或无法创建隔离时，注明真实限制；仅在用户/计划已允许未隔离执行时原地继续。隔离为明确约束时停止依赖它的写入，不自动改到来源工作区实施。原生入口失败后仍保留获准的 Git worktree 自动降级。

**风险**：基线前 main 若已合入 fix/code-audit 而本分支未 rebase，T03 / T04 / T06 会在 AppModel / GUIAppDelegate / SelfTest 上产生合并冲突；按 index 衔接节先处理基点再建 worktree。
